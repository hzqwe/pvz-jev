# PvZ 杂交版 × Jev 自动对战

## 2026-09-26 决策优化

新增前后排约束、按距离/血量/护甲/防守力量/小推车综合评估各路、强力植物储备目标、
近屋救场优先，以及点击前重新读取战场。兼具墙和射手能力的植物会先考虑阻挡；
已有墙但火力不足时，也可以作为后排射手补充。Jev 仍负责候选取舍，代码会拦截
危急时等待、无意义花掉升级预算和已经过期的动作。

继续使用现有 `启动Jev.bat` 即可加载改动。已运行的 agent 需要退出后重启。
详细行为、验证结果和限制见 [决策优化说明](docs/strategy-upgrade.md)。
下面保留的是此前版本的调研记录；与本节有冲突时以最新说明和代码为准。

让 **Jev**（TypeSafe 的 System One 决策模型）来玩《植物大战僵尸 杂交版》。

核心思路就是你说的那条：**代码把战场信息序列化 → 交给 Jev → Jev 返回决策 → 代码执行**。
但有一个关键的分工修正，见下。

---

## 一句话结论：能做，但 Jev 的角色必须是「做取舍」，不是「生成策略」

Jev 是 **System One 决策模型**，它只返回类型化判断（choice / noul / score + 概率），
**不生成自由文本，也不输出动作序列**。所以不能让它"想一套打法然后写出来"。

正确的分工：

| 层 | 谁来做 | 为什么 |
|---|---|---|
| 感知（读战场） | **代码** | 读内存，精确、毫秒级、无歧义 |
| 候选生成（枚举合法动作 + 算威胁/冷却/阳光） | **代码** | 确定性规则，零模型成本 |
| 取舍（这几条合法动作里选哪条） | **Jev** | 这正是它擅长的单维度判断 |
| 校验 + 执行（点击） | **代码** | 合法性、限流、兜底 |

实测依据：Jev 在多目标经济权衡上不可靠（措辞一变结论就翻），但在
"给定选项选一个 / 某维度打分"这类**单维度判断**上稳定可用。所以这里
把"枚举 + 量化"全放在代码里，只把最后那一步判断交给它。

## 已经查实的技术事实

### 逆向 / 打包（静态分析）

| 事实 | 证据 |
|---|---|
| 游戏真实进程是 `PlantsVsZombies.exe`，版本 **1.0.0.1051** | `pvzHE/crash.txt` |
| exe 加载在 **0x400000**（原版布局） | crash 里 EIP `0x0047269B`；运行时实测一致 |
| `main.pak` = **XOR 0xF7** 加密的资源包（非压缩包），内含 8043 个条目 / 392 个 reanim | 解密后索引表可解析 |
| 游戏 exe **不在** pak 里，也不在磁盘上 | 全盘扫描无 PE；由 launcher 运行时释放 |
| launcher 是 PE32，`.rdata` 段 **233MB**（游戏打包在里面） | PE 头解析 |

### 内存偏移（**已在杂交版 v3.9.9 实测**）

```
LawnApp = *(u32*)0x6A9EC0              ✓ 实测 = 0x40AA000
Board   = *(u32*)(LawnApp + 0x768)     ✓ 实测 = 0x54E15170
sun     = *(i32*)(Board + 0x5560)      ✓ 实测 = 400（与游戏内显示的 400 一致）
种子栏   = *(u32*)(Board + 0x144)       ✓ 实测 count=16，type/cooldown 全部合理
game_ui = *(i32*)(LawnApp + 0x7FC)     ✓ 实测 3 = 对局中
game_paused = *(u8*)(Board + 0x164)    ✓ 实测 1 = 菜单开着（时钟停止递增）
```

种子栏已确认无误，且**原版"内联 vs 指针"的歧义已排除**：`*(Board+0x144)` 取指针才对，
直接按 `Board+0x144` 内联读出来是垃圾。卡步长 `0x50`，`type@0x5C`、`cd@0x4C/0x50`。

冷却语义也确认了：**`0x4C` 是剩余冷却 tick，倒数到 0 就绪；`0x50` 是总冷却 tick**。
证据：实测樱桃炸弹 `cd_total=5000`，而 PvZ 樱桃炸弹冷却正是 50 秒 = 5000 tick（100 tick/秒）。

### ✅ 修正：`game_ui` 的语义（之前写错了）

之前 README 里写"`ui=2` 表示正在对局"是**错的**。核对 pvztoolkit 源码后确认：

- `GetScene()` 只在 `ui == 2 || ui == 3` 时才读 scene 字段；
- 多处功能用 `if (GameUI() != 3) return;` 作前置条件。

所以 **3 = 对局中**（实测本机 ui=3 时确实读得到 sun/种子栏），1 = 主菜单。
`offsets.py` 已同步改正。

### ⚠️ 仍未定论：僵尸数组的"活体计数"

按原版 `0x15C` 跨步 dump 僵尸数组原始字节（`tools/find_strides.py`），第 0 槽读出来是：

```
offset 0x00 = 0x040AA000  (LawnApp*)
offset 0x04 = 0x54E15170  (Board*)
offset 0x1C = 0            <- row，合法
offset 0x2C = 865.0 (float) <- x，僵尸刚出屏的位置，合理
offset 0x30 = 250.0 (float) <- y
offset 0xEC = 1            <- dead 标记，命中
```

**字段偏移和步长都对**（所以之前"杂交版把结构体加长了"的推测是**错的**）。
真正的问题是：这个数组是**预分配的对象池**，死掉的槽位里残留着旧数据，
而 `Board+0xA0`（活体数）在杂交版不可靠 —— 草坪全空时按 10 个槽位遍历会捞出
3 个"假活僵尸"。

结论：**不能信 `Board+0xA0`**，必须以 `dead@0xEC` 为准逐槽过滤。
待真实对局（草坪有植物、僵尸真在走）时复核一遍。

### ✅ 修正：`scene` 不是"被挪走"，只是取值超出原版范围

之前实测 `scene=19` 判为异常。后来换了一局（`前院告急 1-5`）读到 **`scene=0`**，
正是"白天草地"，完全正常。所以 19 只是杂交版某个自定义模式的背景 ID
（原版 `SetScene` 只接受 0..5，`SCENE_ROWS` 表查不到就回退 5 行）。
**行数一律以实测为准，不要查表。**

### 界面事实（实测）

- 窗口类名 `MainWindow`，标题 `植物大战僵尸杂交版v3.9.9`，全屏 **2560×1600**。
- **卡槽有 16 格**（原版最多 10），所以任何写死 10 的假设都要改。
- ⚠️ **选卡界面（ui=2）读不到种子栏**：实测这时 16 个槽的 `type_id` 全是 `-1`、
  `cd_total` 全是 0。种子栏是在按下"一起摇滚吧"进关卡之后才填的，
  所以**绑定卡槽必须进关卡再做**。
- ⚠️ **PvZ 最小化会自动暂停**，客户区变成 `0x0`、窗口坐标变成 `-32000`。
  所以任何操作前必须先 `restore_window()`，否则既读不到状态也算不出坐标。
- ⚠️ **PvZ 失去焦点也会自动弹暂停菜单**（实测 `game_paused=1` 且 `game_clock`
  停止递增）。也就是说用户一切出去，agent 就卡死在菜单前面。
  所以 `agent.dismiss_pause()` 是无人值守的**必需**环节，不是可选项。

### 界面几何（已量测并写入 `data/layout.json`）

原版那套 800×600 逻辑坐标（`grid_left=40, cell=80×100, card_stride=52`）
**在杂交版上完全不成立** —— 实测草坪单元宽高比 ≈0.75，原版是 0.80，
说明杂交版重画过草坪底图。套原版值会把点击坐标整体打偏。

量测结果（客户区像素，base 2560×1600）：

| 项 | 值 | 怎么量的 |
|---|---|---|
| `grid_left` / `cell_w` | 386 / **199** | 草坪绿色区域左右外沿 ÷ 9 列 |
| `grid_top` / `cell_h` | 232 / **267** | 上沿取绿区顶；`cell_h` 取**小推车的 y 间距** |
| `card_first_x` / `card_stride` | 189 / **121** | 就绪卡底部米色条的位置与外推 |
| `card_w` / `card_h` | 119 / 172 | 同上 |
| `pause_resume_xy` | **(1270, 1288)** | 暂停菜单绿色文字块的量测值 |

`cell_h=267` 是全场最硬的数：5 台小推车给出 4 个间距（266/267/267），
中位数抖动不到 1px —— 因为推车位置是**游戏按行索引自己算出来的**，
比从美术图里找格线可靠得多（草坪上根本没有可见格线，试过边缘检测，全是纹理噪声）。

`tools/overlay_grid.py` 可以把这套几何画回截图上肉眼复核。当前复核结果：
红线正好压在草坪四沿，5 台小推车各自落在自己的行内，草坪上的浅绿棋盘格
也正好落在对应列内。

**复核工具链**（都在 `tools/`）：`measure_layout.py`（量测+落盘）、
`overlay_grid.py`（画回截图复核）、`look.py`（看一眼当前状态）、
`scan_green.py`（找绿色文字按钮）、`crop.py`（裁一块放大看）、
`find_gridlines.py`（边缘检测找格线，结论是"没有格线"）。

### ⚠️ 一处仍不确定：草坪**行心**的绝对位置

小推车在行心的**下方**（实测约 68px ≈ 0.25 格高），这是**推断**出来的，不是直接量的：

- 若推车在行心，则 `grid_top = 425 - 267/2 ≈ 291`，网格底 = 291 + 5×267 = 1626 > 屏幕高 1600，**放不下** → 矛盾。
- 所以推车必然在行心下方，取 `grid_top = 绿区上沿 = 232`，网格底 1567 < 1600 ✓。

这个推断让**行**上的最大误差约 35px，而格子高 267px —— 点击仍然落在正确的行里。
列的误差更小（左右外沿就是草坪边界）。**所以当前精度足够点击**，
但要更准的话，最可靠的办法是：种一株植物，然后从内存读回它的 `(row, col)`，
和点击坐标对照 —— 这是唯一的 ground truth。`agent` 后续应该加这个自校准。

## 植物功能知识库（这一版的重点）

第一版 `plants.py` 里只有 `id -> (名字, 成本, 角色)`。结果是 **Jev 面对
"樱桃辣椒 vs 阳光炸弹"只能瞎猜** —— 因为两者的 `role` 都是 `instant`，
喂给它的候选描述几乎一样。它看起来在决策，实际上只是在复述启发式分。

现在改成两层数据：

| 文件 | 内容 | 谁维护 |
|---|---|---|
| `data/hybrid_plants.json` | 按**中文名**索引：英文名、成本、角色、**标签**、血量、冷却秒数、**一句英文效果说明** | 人（看图鉴/截图补） |
| `data/lineups.json` | 一局开始时种子栏从左到右的卡面顺序 + 每张卡的期望冷却 | 人（换卡后更新） |
| `data/plant_ids.json` | 名字 ↔ `type_id` 的绑定结果 | `tools/bind_cards.py` 写 |

**标签（tag）是给策略层用的**，比 `role` 细一档，例如：

* `tracking` —— 全屏追踪，**能打任意行** → 不必种在告急的那条路，种在最安全的路就行；
* `splash3` —— 一次性，覆盖自身行 + 相邻两行 → 候选要按"三行僵尸总数"打分；
* `global_freeze` —— 全屏冻结 → 救场按钮，冷却 80s，不能随便交；
* `sun_on_kill` —— 击杀/冻结产阳光 → 既是清场也是经济；
* `wall_regen` / `reflect` / `freeze_on_death` / `charm` / `temporary` …

候选描述现在长这样（Jev 实际看到的就是这段）：

```
Plant "Cherry Chili" (instant, cost 275 sun, 100s cooldown, 300 hp) at lane 2, column B.
Effect: One-shot bomb covering its own lane plus the two adjacent lanes, 1800 damage each.
        Also melts ice trails and cancels freeze slowdown. Long 100s cooldown, so it is a
        real commitment.
Reason: One bomb clears 3 lanes at once (1, 2, 3) which together hold 5 zombie(s), and at
        least one of them has a zombie about to reach the defenders.
```

实测效果（`tools/selftest_decision.py --scenario hybrid`）：Jev 在 0.92s 内
正确指出最危险的是第 1 路（那里有只僵尸在 x=120，已经贴脸），紧迫度 2.97/3，
并选中了覆盖 1~3 路的那颗樱桃辣椒。**这是它自己判断出来的，代码只给了选项。**

### 两道闸门（防止启发式把 Jev 带偏）

启发式分不是排序就完事，还要挡住"看起来分高但实际是浪费"的选项：

1. **一次性爆发必须有僵尸逼近才出候选**（覆盖范围内至少一路 `nearest < 320`）。
   否则平静局面下炸弹会排在最前面，诱导每轮扔炸弹。
2. **全屏冻结要过双重门槛**：整屏 ≥6 只，或者有一路告急**并且**总量 ≥4 只。
   只为了救 2~3 只僵尸交 80 秒冷却的牌是纯亏。

另外 `MAX_PER_TYPE = 2`：同一张卡最多出 2 条落点候选。不加这条的话，
一张三行爆发牌会给出 3~5 个落点选项，把候选列表挤满、其他牌全看不见
（实测场景 3/5/6 都出现了这个问题）。"炸哪一行"确实是真选择，但不该占掉半个列表。

## 卡槽 ID 绑定（换卡池必做，否则 Jev 在看天书）

杂交版每局阵容都不同，**任何硬编码的 `id -> 植物` 表都一定会错**。
所以流程是「名字是稳定事实，ID 靠实测」：

```bash
# 必须**在关卡里**跑（选卡界面读不到种子栏，读出来全是 -1）
python tools/bind_cards.py
```

它做四件事：

1. 读内存拿到种子栏每格的 `type_id`；
2. 按 `data/lineups.json` 里对应 lineup 的 `order` 把名字贴上去；
3. **用冷却时间交叉验证** —— 图鉴给了每株植物的「冷却速度」（秒），
   内存里的 `cd_total` 是总冷却 tick，PvZ 是 100 tick/秒，所以应满足
   `cd_total ≈ cooldown_s * 100`。纯读操作，零成本零风险，区分度也够
   （本局 15 张卡有 7.5 / 30 / 50 / 80 / 100 / 150 秒六种值）；
4. 校验通过才写 `data/plant_ids.json`。**校验不过就不写**，只告警 ——
   宁可让 Jev 看裸 ID，也不能把错的名字挂上去（错了它会拿"樱桃辣椒"的
   价格去判断"豌豆射手"，全盘皆错）。

`agent` 启动时也会自动做一次（第一轮读到 Board 时），所以正常流程下
你只要跑 `run_agent.py` 就行；`bind_cards.py` 是给"想先确认绑定对不对"用的。

还有一道运行时的交叉校验：`agent` 每次点卡都会用**阳光差值**记下真实成本，
如果和知识库里的成本差得远，会打印 `⚠️ 绑定可疑`。这是最后一道防线。

## ⚠️ 跑之前必读：三个会让你误判的坑

这一节是被一次真实故障逼出来的 —— 用户重开一局让 Jev 接管，跑了 150 秒、
37 次决策、**一株都没种上**，而日志看起来每次拒绝都"有据可依"。

### 1. ★ 跑的时候不要切窗口 / Alt+Tab

**PvZ 一旦失去焦点就停止更新**（`game_clock` 冻住）。而且杂交版**不一定显示
暂停菜单** —— 实测抓屏看到的就是一块完全正常的草坪，`find_pause_resume()`
一个绿色按钮都找不到。

这种**「静默暂停」**下 `SetForegroundWindow` 也无效：窗口**本来就已经是前台
窗口**（`GetForegroundWindow() == hwnd`），调用是 no-op、**不产生 `WM_ACTIVATE`**，
游戏内部的 active 标志一直停在 false。

迷惑性极强：**窗口在最前面、画面正常、进程活着，就是时钟不动、点卡没反应。**

- 已实现两级恢复：① 画面上有菜单 → 点「返回游戏」；② 没有菜单 → `minimize → restore`
  制造一次真实激活（`win32.cycle_window()`）。
- 但唤醒动作**会闪窗口、抢焦点**，所以最好还是别切走。主循环里 wake 限 3 次，
  连 3 次拽不回来就只等待，不再反复闪。

### 2. 「点卡被拒」有四种原因，不是"太贵"

`execute()` 用「点卡后阳光有没有掉」来学真实成本（杂交版价格表不可信）。
但"阳光没掉"至少有四种原因：

| 原因 | 该不该记成本 |
|---|---|
| 真的更贵 | ✅ |
| **卡在冷却** | ❌ |
| 阳光不够 | ✅（记下界） |
| **游戏没在处理输入**（暂停/失焦） | ❌ |

把后两类记成"更贵"的后果：几轮之后**每株植物都被记成"要 900+ 阳光"**，
后续决策全变成"保留阳光" → 表现就是**"植物种不下去"**。

顺带查实：**杂交版开局会给部分卡一段初始冷却** —— 实测阳光炸弹/樱桃辣椒/
雪花寒冰菇/回收高坚果/Cupid魅惑菇射手这 5 张（`cd_total=5000`，即 50 秒）
的 `cd_past` 从开局就跟着 `game_clock` 涨，**前 50 秒根本点不动**。
现在 `execute()` 遇到冷却中的卡**连点都不点**，也不会记成本。

### 3. 判据里不能包含"会自己变化的量"

`tools/click_test.py` 原来用「整张快照字符串变了没」判断点击是否生效，
而快照里带了**阳光** —— 阳光会自己涨（天降 + 自动收集），于是
**一株没种上也会报"✅ 生效了"**。实测踩到：`sun 1050→1100`、植物 0 株。

已改成只认 `plant_set()`（**草坪上多了植物**）。
（这是**测试夹具问题，不是产品缺陷**，但它会让真问题溜过去。）

同时确认：**「点卡选种 → 点格子放置」两次点击之间必须隔 ~0.35s**，
否则游戏在同一帧处理完两步、此时"手持种子"还没建立，会出现
**阳光扣了、植物没种上**。

### 已验证：点击注入本身是好的

`tools/click_test.py` 实测种下 `阳光向日葵@r4c0`（阳光 1250→1150，正好 100）。
**后台 PostMessage 有效**，不需要前台真实光标；**点卡的一瞬间就扣阳光**。

## 诚实的边界

* **只读，不改游戏内存**。所有"修改器"能力（无限阳光、秒杀、直接过关…）
  刻意不实现——那是改游戏，不是玩。
* **不处理**：荷叶/花盆/辅助类植物的自动放置、模仿者、需要特殊时机的操作。
  本局阵容里的「睡莲」属于这一类，`policy` 会直接跳过它。
* **阳光收集**靠屏幕颜色识别（亮黄色团块），不是读内存，所以被遮挡时会漏。
* **启发式分是手调的**，不是学出来的。`tools/selftest_policy.py` 的 6 个场景
  只能保证"排序不荒谬"，不能保证"打法最优"。
* **绑定依赖 `lineups.json` 的顺序正确**。顺序错了冷却校验会拦下来（不写文件），
  但如果恰好几张卡的冷却一样（本局有 7 张是 30s），局部错位可能漏检 ——
  最后一道防线是运行时"实测价格 vs 知识库价格"的对比告警。
* Jev 的 `hold_sun` 阈值（0.6）仍是**起点值**，需要在真实对局里调。
  实测它在 hybrid 场景给的 `hold_sun=0.21`（= 不要留钱）是合理的。
