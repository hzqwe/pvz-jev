# Jev 是否需要视觉 MCP / Skill

目前适合采用内存感知为主、视觉补盲的结构。血量、护甲、阳光、卡槽 ID/冷却及对象坐标仍用已有只读内存接口；视觉负责卡面/图鉴核验、特殊地形、暂停/胜负界面和重复落点失败的定位。

TypeSafe 当前文档明确：Jev 的 state 只接受文本或 JSON，不接受图片、音频或视频。因此 MCP/Skill 只是工具接入与操作指南，不能直接让 Jev 获得视觉。若加入视觉，链路应是“截图 → OCR/视觉识别 → 带时间与置信度的结构化事实 → 现有规则校验 → Jev”。[TypeSafe State 文档](https://docs.typesafe.ai/concepts/state)

现有项目已经有窗口截图、像素扫描收阳光及布局坐标模块。无需为了这些已有功能再连接每轮外部 MCP。后续需要补的是识别器与证据融合，而不是重复增加截图工具。

建议分两步接入：

1. 本地低频卡面 OCR / 模板匹配，开局或换图触发，读取成本、卡名、平台与格心。先保存离线识别结果，不直接发送输入；以版本 ID 核验，多个候选或低置信度保持待核对。
2. 仅在未知卡、陌生场景或连续落点失败时调用视觉模型，提取明确字段；设请求预算与超时，不阻塞紧急救场。视觉结果过期、游戏 PID/战场变化或与确认读数冲突时丢弃。

关键观测可保存为 `{game_pid, board_id, clock, observed_at, source, entity_id, confidence, facts}`。价格区分卡面成本与前后净阳光变化；坐标区分视觉格心与实际种植读回。一次截图猜测不改变全局永久绑定或价格。

本轮先实现可靠知识、能力与输入归属，并增强缺失状态诊断。未安装视觉服务或新增视觉 API 消耗。要核实小推车结构或特殊屋顶几何仍需要一次独立的本机只读观测/截图对照；离线测试不能代替这一层。
