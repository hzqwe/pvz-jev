## 1. P0：自己铲植物，被学习器误当成僵尸压扁植物

直接证据：

- 第 108 行，00:04:43：程序铲掉第四路 F 列、3220 血的冰冻坚果，执行结果 `salvaged / completed=true`。
- 第 109 行，00:04:46：紧接着出现 `Learned: zombie_type_7 CRUSHES plants (a Ice Wall-nut vanished instantly under it)`。
- 第 187 行，00:09:45：回收第一路 E 列高坚果，事务记录了 `source_removed`，但拾卡阶段中断。
- 第 188 行，00:09:50：紧接着出现 `Learned: zombie_type_0 CRUSHES plants (a Recyclable Tall-nut vanished instantly under it)`。

`pvz/agent.py:516` 的 `learn_crush_events` 比较两次决策前的植物列表。植物在两次决策之间被自己的铲子移除，也满足“血量大于 700、下一拍消失、附近有僵尸”的条件。它没有排除主动铲除、回收、重开等事件，也没有按采样间隔和附近所有啃食者计算能否被吃掉。一次观察就直接写入硬性 `runtime_crush`。

离线最小复现已确认：前一拍存在 3220 血冰坚果，下一拍移除它并放一个 type 7 僵尸在附近，函数立即学习 type 7 为压扁型。再调用积雪跟踪器，会把该僵尸走过的格子标为积雪，虽然输入中没有任何真实积雪证据。

错误会沿三条路径放大：普通墙被禁用；健康植物被提前铲掉；可种植格被推算为积雪。`decide` 的重开处理只清空僵尸轨迹和积雪，没有清空 `runtime_crush`，因此第一局错误学到的 type 7 会带入第二局。

建议：先排除执行日志中主动移除的植物，按局重置临时学习状态；将未确认行为记为有来源、有有效期的怀疑，多次独立观察后才允许影响硬性规则。把“会压扁”和“会留下冰道”分成独立特征。静态表里 `confirmed=false` 的特征也不应直接作为禁种事实。

验收：主动铲除、回收、长间隔内正常被吃、重开均不能学习压扁；真正有独立压扁证据的类型仍能识别；没有冰道证据不能生成禁种冰道。

## 2. P0：省额度的截断删掉了所有种植理由

`Candidate.describe` 在 `pvz/policy.py:87` 将整段描述截为 240 字符。文字顺序是植物介绍、能力字典，最后才是 `Reason`。

两局共 749 条种植候选描述：749 条全部截断，0 条保留 `Reason:`。`build_questions` 又直接把这段截断文本用作 Choice 选项。
尤其荷叶选项：Jev 看见的是“种荷叶，25 阳光，平台植物”，看不见真正要接上的植物、总成本与保护目的。这些信息虽然存在于内存 Candidate 的 `supports_type / why / covers`，却没有进入候选选项，也没有完整保存在候选日志。

铲子还有语义冲突：统一描述和 action 指令称“铲后变卡片”，但 `salvage=true` 的实际动作是移除植物换阳光；只有可回收高坚果才承诺回收卡片。模型可能把销毁女王理解成可再种植。

建议：改为简短结构化选项，必保留动作类别、目标路与格、真实总成本、实际后续植物、覆盖范围、立即效果、等待后果。植物通用介绍只在卡牌知识里保留一份。分别描述“回收搬家”“铲除换阳光”“铲旧换新”，避免混用。同样保存完整候选和淘汰理由到日志。

验收：荷叶选项明确呈现“荷叶 + 指定植物 + 合计阳光”；每条选项都有当前局面理由；缩减重复知识的同时不丢关键动作字段。

## 建议的实施顺序与验证方式

1. 先修错误学习及跨局污染，同时拆分压扁与冰道。这是会不断扩大损害的根因。
2. 修候选表达和救屋优先级。保持额度约束，但保住动作目的与实际效果。
3. 再调整经济重建、储蓄和阵型建设，用收入与危险时间共同管理预算。
4. 最后改善快速响应、动作适配、回收续接及完整诊断日志。

先把以上日志片段做成离线回归样例：自己的铲子不教坏僵尸知识；重开不继承错误；荷叶后续动作可见；残血荷叶不冒充救屋；180 阳光、2 株产能的安全重建能被考虑。然后用同一批状态比较原版与修改版的候选覆盖和最终决策，再做实战验证。

## 整体审查后的下一步

1. **先量时间，再做短期预测。** 用僵尸实例身份、游戏时钟和连续位置测移速，区分移动、啃食、冻结和击退；预测未来 5～10 秒内墙是否倒下、敌人是否进屋。当前时间筛选没有合并现有火力、控制和多步动作，不能当作保证击杀。
2. **阵型和阳光变成持续目标。** 保留女王 C 列、兼容豌豆 A/B、主墙 E 列以后的目标，记录哪个位置欠缺。用产阳光速度、下一张墙就绪时间和下一波压力计算储备，比较种经济、补输出、攒金卡的收益。
3. **近屋反应从模型请求周期分开。** 高频轻量观察更新风险，紧急时执行可确认的本地拦截；Jev 在安全期比较完整行动方案。记录请求前后时间戳和救场结果，避免 API 延迟吞掉窗口。
4. **扩展日志评测。** 增加受控标注场景：近屋威胁、低威胁经济、安全贵卡、荷叶连招、回收中断。固定少量状态比较策略和提示版本；先验证更少错挡、错铲、空炸和盲等，再看真实胜率。

仍存在的具体限制：铲除/拾回动作校验仍依赖候选列表；冰道融化时间未实测；事务期间没有连续预测移动；模型尚未收到每个动作完整的未来收益比较。这些应作为下一轮明确任务，避免继续堆叠临时分数。
